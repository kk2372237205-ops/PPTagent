## 结论速览

你的三个症状不是"模型不行"，而是**提示词层有 9 个可定位的缺陷**，其中 3 个是代码级的硬缺陷（字段读了一个永远为空的值、代码主动过滤图形词汇、质量检查被明确禁止评价插图）。

| 编号 | 缺陷 | 造成的症状 | 严重度 |
| --- | --- | --- | --- |
| RC-1 | 规划提示词明确允许"0 个画面单元" | 几乎没有插图 | 🔴 高 |
| RC-2 | **代码读 `image_language` 字段，但没有任何提示词要求模型产出它** | 插图很假 + 不统一 | 🔴 **最高** |
| RC-3 | 全套规则没有任何插图面积/尺寸约束 | 插图过小 | 🔴 高 |
| RC-4 | 禁令远多于正向要求，且禁令不给替代品 | 几乎没有插图 | 🔴 高 |
| RC-5 | 代码主动过滤掉 motifs 里的图形词汇 | 插图词汇贫乏 | 🟠 中 |
| RC-6 | 唯一的质检环节被明确禁止评价插图 | 问题永远发现不了 | 🟠 中 |
| RC-7 | **两个开关同时关闭 → "要求画大"与"禁止写实"两条指令都不生效** | 插图很假 | 🔴 高 |
| RC-8 | 三条链路各写一套，无一处定义插图体系 | 全局 | 🟠 中 |
| RC-9 | 画布尺寸与密度规则互相挤压；文字预算只控文字不控画面 | 插图过小 | 🟠 中 |
| RC-10 | **快速版提示词里一条正向插图指令都没有** | 快速版必然没有插图 | 🔴 高 |
| RC-11 | **`visual_evidence: []` 与 `required_visual_evidence_count: 0` 被送进图片提示词** | 模型读到"本页零画面" | 🔴 高 |
| RC-12 | **正文页 `visual_weight` 被代码硬编码覆盖为 `balanced`** | 插图只占一半，且无下限 | 🔴 高 |
| RC-13 | **每页都注入一张"全是矩形"的风格条带并要求几何一致** | 把模型拽向平面几何、无形象 | 🟠 中 |
| RC-14 | 美化 PPT 硬锁蓝金，覆盖员工选的风格包 | 美化链路风格不受控 | 🟠 中 |
| RC-15 | 美化 PPT 不传原图，只传抽出的文字 | "美化"实际是"按文字重画" | 🟠 中 |
| RC-16 | 生图链路固定 1024×1024 且不 resize，与界面承诺的 16:9 不符 | 生图产物非 16:9 | 🟠 中 |

## RC-2（最高优先级）：一个永远为空的字段

这是整条链路里最"值钱"的一个 bug，因为它**既解释了"假"，也解释了"不统一"，而且修起来最省事**。

**代码在读取一个插图语言字段：**

```js
// scripts/deck-generation-worker.mjs:3012
image_language: identity.image_language || identity.imagery || {},
```

**最终图片提示词还专门要求模型遵循它：**

```
// scripts/deck-generation-worker.mjs:3576
- Use the global_style_fingerprint consistently for palette, typography feel,
  background, header/footer, card chrome, motifs, grid, and image language.
```

**但是没有任何一处要求文字模型产出这个字段：**

```js
// scripts/deck-generation-worker.mjs:2536   ← 给 GPT 的输出 schema
"visual_identity":{},
```

```js
// scripts/deck-generation-worker.mjs:2693
"visual_identity": {...符合 visual_identity.json...},
```

而 `skills/deck-generation/visual-identity.md` 定义的 10 个字段是：

```
style_name / palette / background_system / layout_system / card_system /
typography_feel / motifs / header_footer_rules / white_space_rules / forbidden
```

**没有 `image_language`。**

### 后果

1. `visual_identity` 在 schema 里是一个空的 `{}`，GPT 只能自由发挥 → 每套 PPT 生成的字段名可能都不一样；
2. 即使 GPT 恰好产出了 `imagery`，也没有任何规则告诉它**该写什么内容**；
3. 第 12 行读出来是 `{}`，第 3576 行却要求图片模型"遵循 image language"——**模型被要求遵循一份空的合同**；
4. 于是插图风格只能由图片模型自己决定 → 回落训练数据里的默认审美（蓝紫渐变球 / 发光网格 / 玻璃面板）→ **"很假"**；
5. 每页各自决定 → 同一套 PPT 里插图风格漂移 → **"不统一"**。

### 全仓检索证据（可复核）

```powershell
Select-String -Path scripts\*.mjs,lib\*.ts,components\**\*.tsx,skills\**\*.md -Pattern "image_language|imagery"
```

结果：

| 位置 | 性质 |
| --- | --- |
| `deck-generation-worker.mjs:3012` | **唯一的读取点**——读一个没人写入的值 |
| `deck-generation-worker.mjs:3480` | 证据说明，用词是 `decorative imagery must not be copied`（否定） |
| `deck-generation-worker.mjs:3539` | `balancing visible copy and imagery`（中性） |
| `advanced-layout-profiles.md:18` | `Avoid decorative stock imagery`（否定） |
| `advanced-layout-profiles.md:32` | `Avoid weak mood imagery`（否定） |
| `advanced-layout-profiles.md:38` | `Generated technical imagery ... must remain subordinate`（限制） |
| `advanced-layout-profiles.md:60` | `Avoid empty spectacle, generic arrows, and unsupported growth imagery`（否定） |

**两个结论**：

1. `image_language` / `imagery` 在全仓**从未被任何提示词或 schema 要求产出**——第 3012 行读的是一个恒为 `undefined` 的值；
2. 连 `imagery`（画面）这个词本身，在版式规则里出现 4 次，**3 次是否定式、1 次是限制式**——没有一次是"应该画什么"。

再检索 `illustration_system`：**全仓 0 处命中。** 这个项目目前没有任何地方定义"插图该怎么画"。

### 修法

在 `skills/deck-generation/visual-identity.md` 的 JSON 结构里加一个字段，并在 worker 的 schema 里显式要求（`05` 文件给出了完整方案）：

```json
"illustration_system": {
  "style": "flat vector editorial illustration",
  "stroke": "uniform 2px, solid fills only",
  "gradients": "forbidden",
  "shadows": "forbidden",
  "color_count": 4,
  "view": "straight-on orthographic, consistent across all pages",
  "subject_rule": "concrete nouns from page content; abstract nouns forbidden",
  "forbidden_motifs": ["glowing spheres", "neural networks", "glass panels", "..."]
}
```

**并让代码读它**（`3012` 行改成优先读 `illustration_system`）。

## RC-1：规划阶段就合法地允许"不画插图"

给 GPT 的高级版规划提示词里，这两句是"没有插图"的直接授权：

```
// scripts/deck-generation-worker.mjs:2547
- 适合图像表达的正文页优先规划 1-3 个画面单元，高密度页最多 4 个；
  纯文字论证可以为 0 个。

// scripts/deck-generation-worker.mjs:2552
- 严肃汇报、比赛和技术页面的通用装饰图标默认设为 none；
  真实证据不足时使用排版和中性几何，不生成假证据场景。
```

skills 层同一件事写了两遍：

```
// skills/deck-generation/slide-image-specs.md:44
高级版每个适合图像表达的正文页优先规划 1-3 个有语义作用的画面单元；
高密度页最多 4 个，纯文字页可以为 0 个。

// skills/deck-generation/advanced-single-slide-director/SKILL.md:53
Do not force a visual unit when typography or a grounded chart is clearer.
For applicable body pages, prefer one to three meaningful units over empty decoration.
```

### 为什么这必然导致"没有插图"

语言模型在约束下会选**成本最低的合规解**。上面这几句给了两个出口：

- 出口 A：规划 1–3 个画面单元 → 需要想清楚画什么、怎么支撑正文、怎么不违规（成本高、有风险）
- 出口 B：0 个 → 完全合规，零风险（成本最低）

**没有一个字阻止它选 B，也没有一个字要求它说明为什么选 B。** 于是它选 B，而且是静默地选。

同理 `SKILL.md:53` 的 "Do not force a visual unit when typography ... is clearer"——"is clearer"由模型自己判断，它永远可以认为排版更清楚。

### 修法

**反转默认值 + 要求说明理由**（详见 `03-插图手册` T-23 / T-24 / T-30）。

## RC-3：全套规则没有一处写"插图占多大"

现有规则里描述插图规模的字段只有一个自由文本字段 `main_visual_brief`：

```
// scripts/deck-generation-worker.mjs:2555
- main_visual_brief 必须具体说明整体主体、构图、景别、留白方向和情绪，
  并统筹 visual_units；不得只写"科技感""高级感"或重复页面标题。
```

"景别"（framing）不等于面积。模型可以写出"近景特写"却仍然把插图画得只有 20% 大。

结构化字段里也没有尺寸：

```
// skills/deck-generation/advanced-single-slide-director/SKILL.md:85-92
"visual_units": [
  { "supports": "", "form": "", "relationship": "...", "importance": "primary|supporting" }
]
```

`importance` 只有 `primary / supporting`，没有百分比。

最终提示词里唯一的"比例"类要求是**安全边距**：

```
// scripts/deck-generation-worker.mjs:3577
- Keep all important content at least 6% away from every edge.
```

### 为什么这必然导致"插图过小"

生图模型检测到页面里有大量需要精确渲染的中文时，会把像素预算优先给文字，把插图压到"装饰"级别。**没有任何一句提示词要求它不要这么做**，它的压缩是自由行为。

`// scripts/deck-generation-worker.mjs:3569` 虽然提到 scale：

```
- Execute director_contract.main_visual_brief with a deliberate focal point,
  framing, scale and whitespace direction.
```

但 `scale` 的取值来自上一步那份没有数字的自由文本，**约束是空的**。

## RC-4：禁令 >> 正向要求，且禁令不给替代品

`advanced-single-slide-director/SKILL.md` 的 "Hard Boundaries" 一节共 15 条，其中 **12 条是否定式**：

```
:37 Default generic decorative icons to zero...
:38 ...Do not reveal the complete solution too early.
:39 Never create a fake document image to fill a gap.
:40 Never translate dates, people, places, awards, security, products,
    experiments, patents, contracts, or customer proof into generic decorative icons.
:41 Never default to equal-weight card grids.
:42 Never invent readable institution or school signage, logos, certificates...
:43 ...must not be framed as a real campus, customer site...
:44 ...Omit uncertain detail instead of guessing.
:45 ...do not fabricate a recognizable institution facade or sign.
:47 Never use a palette reference as content evidence...
:48 Never display filenames, source locators...
:50 Never render production scaffolding...
:54 Do not place a generated scene behind dense text...
```

正向要求只有 `:53` 一条半（"prefer one to three meaningful units"），而它同时又被 `:53` 前半句否掉。

`evidence-and-authenticity.md` 的 "Control Generic UI Language" 一节（`:36-41`）6 条**全部**是否定式：

```
:38 Generic decorative icon count is zero by default...
:39 Permit a functional icon only when...no clearer typographic or geometric
    treatment exists.
:40 Do not represent a person, date, location, certificate, security claim,
    product feature, experiment, customer, patent, award, or commercial result
    with a stock icon.
:41 Do not use repeated pills, badges, buttons, or equal-weight cards...
```

最终图片提示词里也一样：

```
// scripts/deck-generation-worker.mjs:3572
- Follow director_contract.icon_policy and card_policy. Generic decorative icons
  are zero by default; equal-weight card grids are not the default composition.
```

**这一句包含两条禁令、零个替代方案。** 模型读完只知道"不能画小图标、不能画卡片格"，不知道"那该画什么"。它最安全的选择就是**什么都不画**。

### 关键洞察

> 这些真实性规则**本身完全正确**——不能伪造证书、合同、客户现场、机构招牌。
> 问题在于它们**没有区分两类完全不同的东西**：
>
> | 必须禁止 | 不该禁止 |
> | --- | --- |
> | 伪造证书、合同、报告、专利页 | 概念插画 |
> | 伪造客户现场、真实校园照片 | 机制示意图 |
> | 伪造机构招牌、真人肖像 | 隐喻场景、几何构成 |
> | 伪造数据看板、仿真截图 | 标注式原理图 |
>
> 两类东西在提示词里用的是同一批词（"scene / visual / imagery / illustration"），所以模型一刀切：**全不画。**

**修法**：把 `FABRICATION BAN`（绝对禁止）与 `ILLUSTRATION POLICY`（鼓励且要求）**显式分成两段**（见 `03-插图手册` T-26）。

## RC-5：代码主动删掉图形词汇

```js
// scripts/deck-generation-worker.mjs:3011
motifs: normalizeArray(identity.motifs || identity.decorative_elements)
  .filter(item => !/图标|icon/i.test(String(item))),
```

**这一行的作用**：把风格指纹里所有含"图标"或"icon"的母题**过滤掉**。

于是出现一个荒谬的对比：

| 字段 | 代码怎么处理 |
| --- | --- |
| `motifs`（正向的图形词汇） | **被过滤**，含 icon 的项全部删除 |
| `forbidden`（负向清单） | **完整保留**，一条不删 |

一个只保留禁令、主动削减正向词汇的系统，输出必然是"干净但没有画面"。

### 修法

`motifs` 不应该被过滤，而应该被**扩展**成"可复用图形母题 + 插图母题"两个清单。真正需要过滤的是"把图标当信息载体"这种用法，这在 `icon_policy` 里已经管了。

## RC-6：唯一的质检环节被明确禁止评价插图

```markdown
<!-- skills/deck-generation/quality-audit.md:16 -->
配色变化、一般审美偏差、图标或卡片不够理想、页面之间合理的构图变化都不能触发警告。
```

配套的 `.mjs` 逻辑（grep 确认）只在"空白/损坏/大面积乱码/明显伪造/严重裁切"这类**致命问题**上报警，**不自动重绘**。

### 后果

"插图很小""插图很假""这一页完全没有插图"属于"一般审美偏差"，**在规则层面被明确排除在检查范围之外**。

> 这就是为什么这个问题能一直存在：**它不会被任何自动化环节发现，只能靠人眼发现。** 而生成 12–30 页时，人眼很容易疲劳。

### 修法

不改动"不自动重绘"的原则（那是对的，省钱），但**应该新增一个纯文本的自检项**：让最终那次安全检查顺带报告每页的插图面积估计，把"低于 25%"的页面**列为提示（不是警告）**，由员工决定是否返工。零额外生图成本。

## RC-7：两个开关同时关闭，插图"该画多大"和"不许写实"两条指令双双失效

> ⚠️ **本节是对初版诊断的修正。** 初版曾把 `3561` 行那句 `Do not illustrate nouns from the copy` 列为"当前生效的元凶"；复核后确认**它是死分支，当前根本不会发给模型**。真正的危害恰恰相反——**它不生效才出问题**。

```js
// scripts/deck-generation-worker.mjs:37-41
const advancedImageReferencesEnabled = process.env.DECK_ADVANCED_REFERENCE_IMAGES !== "0";
// Advanced mode reads images only when OCR is necessary. Uploaded source images
// are intentionally not reused as final-slide artwork.
const advancedSourceVisualReuseEnabled = false;   // 第 40 行：硬编码 false
const protectedEvidenceMasksEnabled = false;      // 第 41 行：硬编码 false
```

第 41 行那个开关直接决定 `3656` 行取哪个分支：

```js
// scripts/deck-generation-worker.mjs:3560-3562
options.protectedEvidence
  ? "This request uses a protected evidence mask. … Outside the locked evidence,
     photographic or photorealistic pixels are forbidden: never generate another
     product, device, train, ship, port, person, laboratory, factory, customer site,
     certificate, report, chart, screenshot, or real-world scene.
     Do not illustrate nouns from the copy. Use only audience-facing typography,
     flat presentation surfaces, background texture, lines, and neutral geometry. …"
  : "No source-evidence mask is used. Follow director_contract.visual_strategy,
     main_visual_brief, visual_weight, visual_units, and integration_rule
     as the complete visual brief."
```

因为开关恒为 `false`，**永远走第二个分支**。

### 这个"空档"如何造成"插图很假"

| | 有这条指令时 | 实际（开关关闭） |
| --- | --- | --- |
| "禁止 photographic / photorealistic 像素" | ✅ 生效 | ❌ 不生效 |
| "禁止生成写实产品、写实人物、写实现场" | ✅ 生效 | ❌ 不生效 |
| "只许用排版 + 平面几何" | ✅ 生效 | ❌ 不生效 |
| "必须按 visual_weight / visual_units 执行" | ✅ 生效 | ✅ 生效（但见 RC-12，这个字段被封顶） |

也就是说：**唯一一条能明确禁止"写实感假图"的指令被关掉了**，而替代它的正向指令（`follow visual_weight …`）又指向一个没有尺寸、且被硬编码封顶的字段。

剩下的约束就只有 `3183 / 3571` 的"不得伪造证书、招牌、客户证明"——这条只挡住**具体几类伪造物**，却挡不住**"半写实、半抽象、语义空洞的示意图"**。

> 这就是"插图很假"落进去的那个空档：**既没有"必须画大画清楚"的正向要求，也没有"不许画得像真的"的负向约束。**

### 附：`advancedSourceVisualReuseEnabled = false` 的连带后果

第 40 行关闭后，用户资料里的真实图片**永远不会进入页面**：

```
// scripts/deck-generation-worker.mjs:2550 / 3159 / 3559
用户上传资料中的图片只用于 GPT-5.6 读取文字和含义，不作为最终页面素材
用户资料图片只用于必要的 OCR 和语义理解，不作为 Image2 的页面素材
Uploaded content-source images are intentionally not supplied. … never pretend
a generated scene, document, product, person, campus, or customer site is authentic evidence.
```

这个决定**在真实性上是对的**（不伪造证据），但它等于宣布：**页面上的每一个画面都必须由模型凭空生成**。凭空生成的画面天然更容易空洞、更容易假——尤其当提示词没给它插画语言时（RC-2）。

### 修法

不要简单地把开关打开（那会让真实的校名校徽进入页面，风险很大）。正确的做法是**把"禁止 photographic 像素"这一条从死分支里提出来，让它无条件生效**，同时**补一条允许并鼓励"明确非写实的平面插画"的正面指令**：

```text
ALWAYS APPLY (independent of the evidence-mask switch):
- photographic, photorealistic and documentary pixels are forbidden unless the
  exact image was supplied by the user as confirmed evidence;
- flat, unmistakably illustrative vector graphics ARE permitted and required:
  a clearly non-photographic diagram, mechanism view or conceptual illustration
  drawn with solid fills and uniform strokes may occupy 25%–65% of the canvas.
```

这样"不伪造"和"要有大插图"同时成立。

## RC-8 / RC-9：两条结构性原因

### RC-8 三条链路各写一套，没有一处定义插图体系

| 链路 | 规则来源 | 是否有插图体系 |
| --- | --- | --- |
| 生成 PPT | `skills/deck-generation/**`（13 份） | ❌ 无 |
| 美化 PPT | `scripts/ppt-polish-worker.mjs` | ❌ 待确认（见下） |
| 普通生图 | `scripts/design-agent-worker.mjs` | ❌ 待确认（见下） |

**"风格库 + 版式库"在项目里目前是空的**——`style-packs.md` 有 7 个配色包，`advanced-layout-profiles.md` 有 7 个信息组织语言，但两者的字段里都没有"插图怎么画"和"插图占多大"。

### RC-9 画布尺寸与密度规则互相挤压

```ts
// lib/ai-providers.ts:166
size: trimEnv(process.env.AI_IMAGE_SIZE) || "1536x864",
```

1536×864 是一张不大的画布。而密度规则在**推高**文字量：

```markdown
<!-- skills/deck-generation/content-density.md:14 -->
- 页面空间应被有效使用，避免只有几个空卡片和大面积无意义留白。
```

一边要求"不要大面积留白"，一边期望"插图要大"——在 1536px 宽里，这两件事直接抢像素。插图必然被牺牲。

**修法**：
- 对**插图主导页**（`illustration_share ≥ 55%`）单独放宽密度：`text_density: low`，正文压到 45 词以内；
- 密度规则里补一句例外：`Sparse pages are required whenever the page is illustration-led; do not apply compact density to illustration-led pages.`

## RC-10：快速版提示词里没有一条正向插图指令

快速版与高级版**不是同一套图片提示词**：

| | 快速版 | 高级版 |
| --- | --- | --- |
| 图片提示词函数 | `slidePrompt`（`:3297-3346`），约 3399 字符 | `advancedSlidePrompt`（`:3513-3587`），约 9417 字符 + 合同 JSON |
| 是否带 `pageRenderContract` | ❌ **没有**（`:3199-3201` 对非 advanced 直接 `return persistDeckPlan(...)`） | ✅ 有 |
| 是否有 `visual_weight` / `visual_units` / `icon_policy` | ❌ 全部不存在 | ✅ 存在 |
| 插图相关句子 | **只有负向**（见下） | 正负都有（但见 RC-1/RC-11/RC-12） |

快速版图片提示词里与画面有关的**全部**内容：

```
// scripts/deck-generation-worker.mjs:3334
- Output a full 16:9 PPT page, not a poster, not an isolated illustration.

// scripts/deck-generation-worker.mjs:3344
- Use concise designed text only when needed. Prefer clean information blocks
  over long paragraphs.

// scripts/deck-generation-worker.mjs:3340
- Keep every important title, chart, icon, and bottom banner inside a safe area…
```

**"Prefer clean information blocks over long paragraphs"** 这一句是**反向推**：它明确告诉模型"优先干净的信息块"。加上唯一提到"illustration"的地方是 `not an isolated illustration`（否定），快速版在提示词层面**没有任何理由画插图**。

> 结论：**快速版没有插图不是模型的问题，是提示词里真的没要求。**

## RC-11：合同里明写着"零张视觉证据"

`pageRenderContract()` 生成的合同里有这两个字段，并被 `JSON.stringify(contract)`（`:3549`）**原样送进图片提示词**：

```js
// scripts/deck-generation-worker.mjs:3101 / :3148
visual_evidence: [],

// scripts/deck-generation-worker.mjs:2457
required_visual_evidence_count: 0,   // visualEvidenceJson 恒为 "[]"（:2651）
```

模型读到的字面意思是：**"本页需要 0 张视觉证据。"**

人类知道这两个字段是给"真实资料证据遮罩"用的（而那个功能被关掉了），但**图片模型不知道**。它看到一个明确写着"零张视觉素材"的合同，很自然地推出"这一页不需要任何画面"。

### 修法

要么把这两个字段在关闭该功能时**从合同里删掉**（不要发空数组给模型），要么改名并加注释，例如：

```json
"verified_evidence_assets": { "count": 0, "note": "no user-supplied evidence images are used on this page; all visuals are generated illustrations" }
```

## RC-12：正文页的"画面比重"被代码封顶在 `balanced`

`visual_weight` 是这套系统里唯一的"图文比重"字段，取值 `text-led / balanced / visual-led`。GPT-5.6 会给出它的判断，但 `normalizeDirectorContract` **会覆盖它**：

```js
// scripts/deck-generation-worker.mjs:2380-2384
const visualWeight = page.role === "cover" || page.role === "ending"
  ? "visual-led"                                    // 封面/结尾：强制视觉主导
  : effectiveVisualStrategy === "typography"
    ? "text-led"                                    // 选了排版：文字主导
    : "balanced";                                   // ← 其余所有正文页：一律"均衡"
```

于是**所有正文页的画面比重上限就是 `balanced`**，`visual-led` 这个档位在正文页**永远拿不到**。

而且 `balanced` 没有任何量化定义——`3178` 行只说"`visual_weight` 决定本页文字与画面的相对比重"，没说均衡等于百分之几。模型只能自己猜，猜出来的就是"文字为主、画面点缀"。

### 修法

给三档写上面积定义（这比新增字段更省事，且立刻生效）：

```
text-led  → illustration occupies 15%–25%
balanced  → illustration occupies 35%–45%, and it is the second largest element
visual-led → illustration occupies 50%–70%, and it is the largest element
```

## RC-13：每页都被塞进一张"全是矩形"的风格条带

高级版每一页都会额外收到一张参考图 `deck-style-strip.png`，role 文本是：

```
// scripts/deck-generation-worker.mjs:3422
"deck-wide style strip; keep its palette roles, header/footer rhythm, grid,
line weight and geometry consistent on every page"
```

而这条带子是 `createDeckStyleStrip`（`:3042-3068`）用 SVG 现画的，**全部元素是 `<rect>` 和直线**（`:3050-3063`）。

**后果**：图片模型在 `/images/edits` 里同时收到"文字合同"和"一张由矩形组成的参考图"，并被要求"保持几何一致"。这会把输出系统性地拽向**平面几何构图**——干净的色块、直线、边框，而**没有任何形象化的东西**。

这与 RC-2（插图语言为空）叠加，正好解释了为什么产出的"插图"经常是**圆形 + 线条 + 灰色占位条**，而不是有内容的画面。

## RC-14 / RC-15：美化 PPT 链路的两个独立问题

### RC-14 员工选的风格被硬编码蓝金覆盖

```js
// scripts/ppt-polish-worker.mjs:268
"- Use one consistent deck identity across every page: deep navy base,
 electric blue light trails, refined gold highlights, glassy dark cards,
 clean sans-serif Chinese typography, and the same icon stroke style."

// scripts/ppt-polish-worker.mjs:270
"Do not suddenly switch to a red/black, orange, purple, beige, cartoon,
 hand-drawn, or poster-only style. Even crisis/risk pages must stay in the
 blue-gold tech system."
```

员工在界面上选了"白绿科技 / 红白政企 / 极简学术 / 活力路演"时，提示词里只有一句中文名：

```js
// scripts/ppt-polish-worker.mjs:316
`Target style: ${stylePackName(run.stylePack)}`
```

**中文名 vs 硬编码的英文蓝金锁**——后者是具体描述，前者是四个字。模型会听具体的那一个。这 4 个风格包在美化链路里**实际上选不了**。

### RC-15 "美化"看不到原页面

美化链路只从 PPTX 里抽文字，不传原图：

```js
// scripts/ppt-polish-worker.mjs:209
const texts = Array.from(String(xml || "").matchAll(/<a:t[^>]*>([\s\S]*?)<\/a:t>/g))
// :216
originalText: cleanText(uniqueTexts.join(" / "), 1800)
```

然后走**纯文生图** `/images/generations`（`:151`），提示词通篇没有原版式或原图引用。

**所以"美化 PPT"实际执行的是"读懂文字后重新画一页"**——原版式、原图表、原配图全部丢失。这不是 bug，是设计如此，但它与"美化"这个词的语义不符。如果员工期望的是"保留我的版式只换视觉"，那需要改成 `/images/edits` 并把原页面图作为输入。

# 真实产出证据（三张实际生成的页面）

下面三张图都是从 `uploads/employee-workspace/images/` 里**实际生成的成品**（只读查看，未修改）。它们构成一个**天然对照实验**，直接证明了上面的诊断。

## 案例 A：封面页 —— 好，因为 `visual_weight` 被强制成 `visual-led`

- 文件：`1787021555018-601eaaa5afafb.png`（1920×1080）
- 内容：《需求互嵌 二三联动 —— 行业高职院校与大型国有企业合作育人的创新与实践》
- 表现：**右侧 55% 是一整幅出血的高铁 + 城市天际线 + 电力设施场景**，向左渐隐融入标题区，下方是三段式色带（为高铁供电 / 为湾区育才 / 为出海送教）
- 为什么它好：`2380-2384` 行强制封面 `visual-led`，且 `SKILL.md:45` 要求封面"build a strong thematic composition … do not fabricate a recognizable institution facade"
- **它证明模型的画图能力没问题**——问题在指令。

## 案例 B：正文页 —— 差，11 个碎片化小图标 + 5 张糊图，没有主视觉

- 文件：`1786256643920-1a79e56636d368.png`（1920×1080）
- 内容：《07 定向培养 | 校企协同打通培养就业链条》，5 步流程 + 右侧 4 个指标
- 实际画面构成：

| 元素 | 数量 | 单个约占画布 | 性质 |
| --- | --- | --- | --- |
| 圆形小图标（数据/人群/书本/清单/列车） | 5 | ~1% | 通用装饰图标（提示词要求为 0） |
| 底部小缩略图（机房/会议室/文档/工位/列车） | 5 | ~4% | **模糊的假照片** ← 这就是"插图很假" |
| 右侧指标旁小图标 | 4 | ~1% | 通用装饰图标 |
| **主视觉** | **0** | **0%** | **完全没有** |

- 全部画面碎片加起来约 25%，但**没有任何一个元素超过画布的 5%**
- 这正是 `RC-3`（无面积约束）+ `RC-12`（正文页封顶 `balanced`）+ `RC-4`（禁令无替代）的联合产物
- 注意：提示词明确写着 "Generic decorative icons are zero by default"（`:3572`），但页面上有 **9 个通用图标**——**因为提示词只禁了图标，没要求插图，模型就用了它最熟的默认方案**

## 案例 C：正文页 —— "假"的典型形态：抽象圆 + 灰色占位条

- 文件：`1786894198805-fc1913ad25b808.png`（1920×1080）
- 内容：《为什么需要图文相辅相成的演示页面》（高级版图文关系最小试跑，1/2 页）
- 实际画面构成：1 个深色大圆（核心结论）+ 3 个浅色圆（支撑机制）+ 细连线 + **圆内 3 组灰色横条**
- 那 3 组灰色横条是**没有任何语义的占位符图形**（看起来像 lorem ipsum 的视觉版），旁边配 3 个极小的图标
- 这一页的画面约占 40%，**面积是够的，但它"假"** —— 因为它是"图形的排列"，不是"内容的表达"

**案例 C 精准对应 `RC-2`**：模型不知道该用什么插画语言，于是画了最安全的"圆圈 + 线条 + 占位块"。它满足了所有禁令，也没有触犯任何真实性规则，但**什么也没说明**。

## 三个案例的结论

| | 案例 A 封面 | 案例 B 正文 | 案例 C 正文 |
| --- | --- | --- | --- |
| `visual_weight` | `visual-led`（代码强制） | `balanced`（代码默认封顶） | `balanced`（代码默认封顶） |
| 主视觉面积 | ~55%，出血 | **0%** | ~40%（但无语义） |
| 问题 | 无 | 插图过小 / 没有插图 | 插图很假 |
| 对应根因 | — | RC-3 / RC-4 / RC-12 | RC-2（+ RC-13） |

> **同一个模型、同一套风格包、同一批任务，唯一的差别是"画面比重"这个字段有没有被强制拉高。**
> 这是"问题在提示词层、不在模型层"的最直接证明。

## 附：关于画布尺寸的更正

初版诊断（基于代码默认值）写的是 `1536×864`。实际 `.env` 覆盖为：

```
AI_IMAGE_SIZE="1920×1080"
```

**实测真实产出确实是 1920×1080**（案例 A/B/C 全部为 1920×1080，比例 1.778）。所以：

- ✅ 分辨率不是"插图过小"的原因，1920×1080 够用；
- ⚠️ 但 `.env` 里用的是**全角乘号 `×`（U+00D7）**，而代码默认值是 ASCII `x`：

  ```
  .env：  AI_IMAGE_SIZE="1920×1080"   ← 第 5 个字符是 U+00D7
  代码：  size: trimEnv(process.env.AI_IMAGE_SIZE) || "1536x864"   ← ASCII x
  ```

  这个字符串被原样发给中转站（`lib/ai-providers.ts:166` → `ai-service-client.mjs:97-104`，无任何归一化）。**中转站是否接受全角乘号尚未验证**——从实测产出是 1920×1080 来看，很可能被接受了或至少回落到了 16:9。
  **建议**：把 `.env` 改成 ASCII 的 `1920x1080`，消除这个不确定性（`.env` 不在 Git 里，属于本机配置，请自行修改）。
